# PHM Engine Predictive Maintenance — Data Generator

## 1. Domain Overview

This project simulates a fleet of aircraft turbofan engines monitored by a real-time predictive maintenance system. The data generator produces:

- **Offline historical data** (`simulated_FD002.txt`) — a two-stage dataset per engine combining a synthetic healthy phase with real NASA C-MAPSS degradation trajectories, stored in GCS.
- **Streaming telemetry events** — individual engine cycle snapshots published as JSON to GCS raw buckets, consumed by the feature platform in near real-time.

The goal is to support downstream ingestion, feature engineering, model training, and online inference while injecting realistic operational characteristics present in real turbofan fleet data.

---

## 2. Source Dataset

**Dataset:** NASA C-MAPSS FD002 sub-dataset.

| Attribute | Value |
|---|---|
| Training engines | 260 |
| Test engines | 259 |
| Operating conditions | 6 (combinations of altitude, Mach, TRA) |
| Fault mode | HPC (High-Pressure Compressor) degradation |
| Columns | 26: unit_id, cycle, 3 operational settings, 21 sensor measurements |
| Sensor measurements | T2, T24, T30, T50, P2, P15, P30, Nf, Nc, epr, Ps30, phi, NRf, NRc, BPR, farB, htBleed, Nf_dmd, PCNfR_dmd, W31, W32 |

**Reference:** A. Saxena, K. Goebel, D. Simon, N. Eklund, *Damage Propagation Modeling for Aircraft Engine Run-to-Failure Simulation*, PHM08, Denver CO, Oct 2008.

## 3. Offline Dataset Design

### 3.1 Two-Stage Simulation

The generator (`generate_simulated_FD002.py`) extends raw C-MAPSS data with a synthetic healthy phase before each engine's degradation trajectory, producing a realistic fleet simulation:

| Stage | Description | Cycles per engine | RUL calculation |
|---|---|---|---|
| Stage 1 — Normal | Synthetic healthy cycles generated by adding Gaussian noise (σ=0.01) to the engine's first observed baseline cycle. Operational settings are preserved exactly. | 50 cycles | `(50 − current_cycle) + max_degradation_cycles` |
| Stage 2 — Degradation | Original C-MAPSS FD002 training rows, with time index continuing from Stage 1. | Variable (avg ~208 cycles) | `max_cycle − current_cycle` |

**Output:** `simulated_FD002.txt` — whitespace-delimited, 26 columns, one row per engine-cycle. Total rows: ≈ 67,340 (260 engines × avg 258 cycles).

### 3.2 Data Volume

| Metric | Value |
|---|---|
| Total simulated rows | ~67,340 |
| Producer batch size per CronJob run | 50 rows (configurable via `CYCLES_PER_RUN`) |
| CronJob frequency | Every 5 minutes |
| Approximate throughput | 10 rows/minute (~600 rows/hour) |
| Time to replay full dataset | ~112 hours at default rate |
| GCS raw event size per row | ~1.2 KB JSON |

### 3.3 Streaming Event Schema

The producer (`producer.py`) reads `simulated_FD002.txt` row by row using a GCS checkpoint (`checkpoints/FD002/last_row.json`) and publishes each cycle as a JSON event to `gs://phm-raw-data-aide2-494008/raw_engine_cycles/FD002/`:

```json
{
  "unit_id": 1,
  "cycle": 52,
  "dataset": "FD002",
  "timestamp": "2026-05-19T09:16:31Z",
  "sensors": {
    "OperSet1": 34.9983,
    "OperSet2": 0.8400,
    "OperSet3": 100.0,
    "SensorMes1": 449.44,
    "SensorMes2": 555.32,
    ...
    "SensorMes21": 8.8071
  }
}
```

### 3.4 Data Problems Injected

**Compulsory:**
- **Multi-condition skew**: FD002 uses 6 distinct flight conditions. Engines cycle between conditions non-uniformly, causing sensor distributions to be multi-modal rather than Gaussian.
- **High cardinality identifiers**: `unit_id` (1–260), `cycle` (1–400+) — unique combinations are essentially primary keys.
- **Schema evolution risk**: The Stage 1 synthetic rows use the same schema as Stage 2, but downstream consumers must handle potential `RUL` field absence in the test set (test data has no RUL labels by design — RUL is provided separately in `RUL_FD002.txt`).

**Optional chosen:** The Stage 1 synthetic sensor values include small Gaussian noise (`noise_std=0.01 × |baseline_value|`) applied independently per sensor per cycle, simulating real sensor jitter and creating mild measurement uncertainty without changing the healthy-state distribution significantly.

### 3.5 Generator Configuration

```yaml
data_dir:      data/CMaps/            # source C-MAPSS files
output_dir:    data/CMaps/            # output simulated file
normal_cycles: 100                    # synthetic healthy cycles per engine (README default; code default: 50)
noise_std:     0.01                   # Gaussian noise multiplier
random_seed:   42                     # reproducibility
dataset:       FD002
```

## 4. Validation Layer

The validation service (`validation_service.py`) runs as a CronJob offset 2 minutes after the producer, consuming raw events from GCS and routing them:

- **Valid** → `validated_engine_cycles/FD002/` (consumed by Flink stream processor)
- **Invalid** → `invalid_engine_cycles/FD002/` (quarantined in quality bucket)

Four Great Expectations suites are applied in sequence:

| Suite | Checks |
|---|---|
| schema | All 26 columns present, correct data types |
| null | No missing values in any sensor or operational setting |
| range | Each sensor within C-MAPSS FD002 observed bounds (e.g. SensorMes1: 400–550°R) |
| order | `cycle >= 1`, `unit_id >= 1`, monotonically increasing per engine |

**Observed validation rates:** ~99.8% pass rate; failures are primarily out-of-range sensor values from the noise injection edge cases.

## 5. Feature Engineering

The Flink stream processor (`flink_job.py`) computes windowed features from validated events. Features are derived from 14 selected sensor columns after dropping low-correlation sensors for FD002:

**Dropped columns (low RUL correlation):** `OperSet1`, `OperSet2`, `OperSet3`, `SensorMes1`, `SensorMes5`, `SensorMes10`, `SensorMes18`, `SensorMes19`

**Retained feature columns (14):** `OperSet3`, `SensorMes2`, `SensorMes3`, `SensorMes4`, `SensorMes6`, `SensorMes7`, `SensorMes8`, `SensorMes9`, `SensorMes11`, `SensorMes12`, `SensorMes13`, `SensorMes14`, `SensorMes15`, `SensorMes16`, `SensorMes17`, `SensorMes20`, `SensorMes21`

**Feature store outputs:**

| Store | Target | Grain | Refresh |
|---|---|---|---|
| Redis online store | Latest 30-cycle rolling window per engine | `engine:unit_id:window` key | Every 5 minutes (CronJob) |
| PostgreSQL offline store | Historical feature rows with RUL labels | `(unit_id, cycle, dataset)` unique | Every 5 minutes (CronJob) |

## 6. Deliverables

1. **Generator code:** `services/data-ingestion/src/generate_simulated_FD002.py` — configurable via CLI arguments.
2. **Producer code:** `services/data-ingestion/src/producer.py` — checkpointed GCS streaming publisher.
3. **Validation code:** `services/data-ingestion/src/validation_service.py` — Great Expectations four-suite validation.
4. **Sample outputs:** `data/CMaps/simulated_FD002.txt` (67,340 rows), raw JSON events in GCS.
5. **Quality evidence:** Monitoring dashboard log stream showing `[INFO] All validated events already processed` and `[WARNING] INVALID` routing in `assets/imgs/monitoring_UI.png`.
6. **Write-up:** Two-stage design chosen because C-MAPSS engines have no healthy-phase data — the synthetic Stage 1 enables anomaly detection training on a clean normal pool (`RUL > 150`) without data leakage from the degradation trajectory.
